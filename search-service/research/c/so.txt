## Context

A self-hosted SearXNG (17 engines, per-engine `weight:` keys tuned) used as the search backend for several coding agents. Engine curation and weighting had already been done and measurably helped ranking, but result _relevance_ stayed poor: a real-estate site sat at #2 for a smart-home software query, and a dating site appeared for a query about a town's childcare registration.

## The structural cause

SearXNG is **rank fusion, not relevance**. Its score is roughly

```
score = (product of engine weights) * (number of engines agreeing) * sum(1/rank)
```

It never reads the query text or the page. A result that a single heavy engine returned at rank 1 gets that engine's full weight regardless of topic — so anything matching one common word from the query rides straight into the top slots. No amount of `settings.yml` tuning fixes this, because the information needed (is this page about the question?) is not in the inputs.

## What worked: veto, not rerank

Add a small LLM pass between SearXNG and the consumer that sees only `host | title | snippet` for the top ~24 results and returns **the indices to drop**. Ordering is left entirely to fusion.

I tried reranking first (ask the model to reorder by relevance) and it **regressed** strong-consensus queries — 5/6 relevant in the top 6 down to 3/6 — because SEO pages carry titles matching the query verbatim, and the model preferred them over the primary source that several engines had independently agreed on. Fusion's consensus signal is genuinely good at ordering; it is only blind to topic. So: the model gets a veto, never a promotion.

Prompt shape that mattered — bias it hard toward keeping:

```
Return the indices of results that clearly CANNOT help answer the question.
Drop: results matching only a common word from the question; homepages and
brand landing pages with no substantive content; an unrelated subject.
Keep: anything plausibly on topic, even if low quality; anything you are unsure about.
Be conservative: dropping a good result costs more than keeping a bad one.
Return ONLY a JSON array of integers.
```

## Numbers

40 queries across dev tooling, infra/ops, AI/LLM, home automation, non-English local-government queries, and short ambiguous brand-collision queries. **Paired design**: SearXNG was queried _once_ per query and both conditions derived from that same result set — engines time out independently, so back-to-back identical queries return visibly different sets and an unpaired A/B buries the effect in noise. Relevance judged blind (union of both conditions' URLs shuffled per query, judged without knowing which condition produced which).

|  | precision@8 |
| --- | --- |
| fusion alone | 55.0% (176/320) |
| + veto pass | 74.1% (237/320) |

29 queries improved, **0 regressed**, 11 unchanged. The unchanged ones were queries where engine consensus was already strong — nothing to drop. Biggest gains were exactly the predicted failure mode: ambiguous place names and product names colliding with unrelated brands, 3/8 → 8/8.

## Two operational gotchas

1.   **Turn thinking off on the screening call.** With reasoning enabled the model emitted ~9k characters of reasoning to produce a 13-number array: 22.7s vs 1.7s for an _identical_ verdict. Screening is a judgement call, not a reasoning problem. Net latency of the whole pass then becomes ~0.8s (2.3s → 3.1s end to end).
2.   **Ship it as a proxy that speaks SearXNG's own API**, not as a new endpoint. Every existing client (agent frameworks, MCP servers) then moves by changing one base URL. Forward everything unchanged and post-process _only_ a JSON `/search` response — the HTML UI, `/config` and static assets must stay byte-for-byte, or the web UI breaks. Read the query from SearXNG's own echoed `query` field in the response rather than parsing the request body: that handles GET and POST identically and avoids a multipart-parser dependency.

Fail open — if screening errors or times out, return plain SearXNG results and set a response header saying so. A search backend that returns nothing is worse than one that returns junk.

## When this is not worth it

If your queries are mostly high-consensus (well-known library names, exact error strings), expect little change — that was the 11 unchanged queries. The gain concentrates on ambiguous, local-language, and brand-colliding queries.
